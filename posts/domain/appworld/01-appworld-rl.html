(2606) SIRI: Self-Internalizing Reinforcement Learning with Intrinsic Skills for LLM Agent Training ​

🌺 论文摘要

SIRI 论文摘要

参考链接

  • paper, code

核心方法

  • SIRI：让Agent自己挖Skill、验证Skill、再把Skill内化到模型参数。
  • 三阶段训练：
    • Policy Warmup：先用GiGPO把Policy训到能产生可靠成功轨迹。
    • Self-Skill Mining：只从自己的成功轨迹中总结Skill，不依赖外部Skill生成器。
    • Skill Internalization：把真正有效的Skill轨迹蒸馏回Plain-Prompt Policy。
  • Skill有效性验证：同一个任务同时做带Skill/不带Skill的配对Rollout，只有能提高Reward的Skill才保留。
  • 最终部署：训练完丢掉Skill Bank + Retriever，推理时不再注入Skill。

模型效果 (Qwen2.5-7B-Instruct)

  • ALFWorld：SIRI Success 0.930，高于GiGPO 0.908和SkillRL 0.899。
  • WebShop：SIRI Score / Success 0.899 / 0.813，高于GiGPO 0.844 / 0.728和SkillRL 0.852 / 0.727。
  • 论文没有在AppWorld上做实验，AppWorld只作为长程Agent RL相关背景引用。

重要结论

  • Skill可以只做训练期Privileged Information，不一定要在推理时继续检索。
  • 先Warmup很重要：从未训练Policy的低质量轨迹里总结Skill，反而会污染后续学习。
  • 不能整条轨迹无脑蒸馏：
    • Trajectory层面先判断这个Skill是否真的有用。
    • Action层面只学习正优势的可执行Action Token。
  • 外部强模型生成Skill主要帮助训练早期；Policy变强后，自挖掘Skill可以逐渐追上。

关键贡献

  • 提出无需外部Skill Generator的自挖掘Skill RL流程。
  • 提出Advantage-Weighted Skill Internalization，使最终Agent实现Retrieval-Free Inference。
  • 将RL Credit用于两个对象：既优化Action，也评估“哪个Skill值得被内化”。

问题背景(外部Skill依赖) ​

❓问题背景

Skill增强Agent的两类依赖

训练依赖

  • 现有方法常使用外部LLM、独立Trajectory Distiller或Skill Manager生成Skill。
  • 训练效果部分来自辅助模型，而非Agent自身能力演化，增加工程和计算成本。

推理依赖

  • Skill长期保存在Skill Bank中，每个任务都要检索并注入Prompt。
  • 带来更长Context、检索延迟和额外部署组件，也会造成Train/Inference接口不一致。

核心问题

  • Agent能否在RL中自己发现Skill、验证Skill，并将其吸收进Policy参数，使部署时完全不需要Skill Bank？

核心方法(SIRI三阶段课程) ​

📕核心方法

Phase 0: Policy Warmup
  • 使用GiGPO训练Plain-Prompt Policy，获得基本交互能力。
  • GiGPO同时提供Episode-level Advantage和Anchor-state Step-level Advantage。
  • 只有无Skill Rollout且Return超过成功阈值的轨迹，才进入后续Skill Mining。
  • 当成功轨迹数量达到阈值，或Warmup达到最大步数时，进入下一阶段。

作用

  • 避免错误Skill：未训练Policy中的偶然成功，很容易被误总结成通用经验。
  • 提供高质量经验：先获得足够多的成功轨迹，再进入Skill Mining。
Phase 1: Self-Skill Mining and Utilization

Self-Mining

  • 冻结当前Policy的Snapshot，从成功Plain Rollout中总结Condition-Strategy形式的自然语言Skill。
  • Skill状态包括candidate / active / retired，并记录在线效用、检索次数和适用场景。

Paired Validation

  • 同一任务组一半使用Skill，一半不使用Skill。
  • Skill宏观效用定义为两组平均回报差：
Δg=Rgskill−Rgbase
  • 用EMA更新Skill效用；检索次数足够且效用为正的Skill才升级为Active，持续负效用Skill被Retire。
Phase 2: Advantage-Weighted Skill Internalization

Teacher / Student共享参数、输入不同

  • Teacher使用Skill-Augmented Context生成Action。
  • Student在Plain Context下学习复现Teacher Action。

两层过滤

  1. Trajectory Utility Gate：仅当 Δg>0 时，才蒸馏Skill分支轨迹。
  2. Action Advantage Weight：只蒸馏可执行Action Token，并按GiGPO正优势加权；Reasoning文本和低优势Action不进入Internalization Loss。

也就是说：先回答这个Skill有没有用，再回答轨迹里的哪些Action值得学。

联合目标

Ltotal=LGiGPO+βLKL+λ(k)Lint
  • 训练结束后丢弃Skill Bank，推理只使用原始任务Prompt。

实验设置 ​

✍️实验设置

实验设置

基础模型

  • Qwen2.5-7B-Instruct，附加实验验证Qwen2.5-1.5B。

训练与评测环境

  • ALFWorld：6类具身家务任务。
  • WebShop：长程商品搜索与购买任务。
  • 未评测AppWorld，因此不能把SIRI数值与AppWorld方法直接比较。

训练配置

  • 8张A100 80G；每批16个任务，Group Size 8。
  • Warmup最少30步、最多50步；每10步进行Skill Mining和验证。
  • Retriever使用Qwen3-0.6B-Embedding。

关键结果 ​

🍑关键结果

模型效果与消融

主结果

  • ALFWorld Overall：SIRI 0.930 > GiGPO 0.908 > SkillRL 0.899。
  • WebShop Success：SIRI 0.813 > GiGPO 0.728 ≈ SkillRL 0.727。
  • WebShop Score：SIRI 0.899 > SkillRL 0.852 > GiGPO 0.844。

消融 (WebShop)

  • 去掉Warmup：Score / Success为0.850 / 0.711，说明低质量初始轨迹会污染Skill Mining。
  • 去掉Internalization但推理继续带Skill：0.898 / 0.805，说明Skill Bank本身质量较高。
  • 去掉Internalization且推理不带Skill：0.852 / 0.719，说明Policy尚未自动吸收外部Skill。
  • 完整SIRI：0.899 / 0.813，在不带Skill推理时反而最好。

GRPO兼容性

  • SIRI不仅适用于GiGPO；基于GRPO也把WebShop Success从0.568提升到0.648。
  • 但GiGPO更细粒度的Credit Assignment能提供更好的Warmup轨迹，最终上限更高。

未来方向 ​

⛳未来方向

未来展望
  • 当前Skill Mining能力只是随Policy整体能力间接提升，没有专门优化“如何总结Skill”的训练信号。
  • 需要在AppWorld等API交互环境验证自挖掘与无检索部署是否仍有效。
  • Skill Utility依赖少量配对Rollout，未来可研究更低方差、更节省环境交互的在线评估。
  • 可进一步研究与Skill-SD的差异：SIRI选择性蒸馏Action Token，Skill-SD则使用跨Prompt Importance-Weighted Reverse-KL。

(2606) GVPO: Group Verification-based Policy Optimization for Interactive Coding Agents ​

🌺 论文摘要

GVPO 论文摘要

参考链接

  • paper

核心方法

  • GVPO：最终Unit Test奖励 + 中间代码执行反馈。
  • AppWorld每一步代码执行都会返回成功 / Syntax Error / Runtime Exception，这些都是免费的Process Reward Signal。
  • Advantage Shaping：
    • 最终Unit Test仍决定整条Trajectory好不好。
    • 中间失败Step再做局部惩罚，避免错误代码也被正向强化。
  • 训练细节：Sequence-Mean-Token-Mean + 非对称Clip + 不除以组内std + 去掉KL。
  • 不需要训练额外的Reward Model。

模型效果 (Qwen2.5-32B-Instruct, AppWorld)

  • Test-N：TGC 72.6 / SGC 55.4。
  • Test-C：TGC 49.4 / SGC 28.8。
  • 相比LOOP，在Test-C提升+3.7 TGC / +2.2 SGC；相比OpenAI o1提升+12.7 TGC / +9.4 SGC。

重要结论

  • Outcome-only的Credit太粗：成功轨迹里的错误Step也会被奖励，失败轨迹里的正确探索也会被一起惩罚。
  • 环境报错可以把Trajectory-level Credit进一步细化到Step-level。
  • GVPO学出了更谨慎的Query-before-Act行为：先查API文档，再真正执行，Step失败率更低。
  • 惩罚不能太大：过强Process Penalty会让Agent不敢探索，论文中 b=0.2 最稳。

关键贡献

  • 提出统一Outcome与Process Verification的Agent RL Advantage Shaping框架。
  • 在不引入额外Reward Model的情况下实现Step-level Credit Assignment。
  • 系统验证Loss Aggregation、Asymmetric Clip、Std Normalization和Shaping形式对AppWorld训练的影响。

问题背景(Outcome Reward过于稀疏) ​

❓问题背景

GRPO对长程Agent的Credit Assignment不足

Outcome-only RLVR

  • AppWorld最终通过Unit Test给出任务级奖励，但奖励只在轨迹结束后出现。
  • GRPO将同一条Trajectory的Group-relative Advantage广播给所有Token。

两类错误Credit

  • 成功轨迹：可能包含语法错误、错误API和多余重试，但这些Step仍得到正优势。
  • 失败轨迹：可能包含正确探索或正确API调用，但所有Token又被一起负向更新。

被忽略的环境信号

  • Interactive Coding Agent每轮都会执行代码，环境天然返回成功、异常和错误信息。
  • 这些反馈比最终Unit Test更密集、可验证，却没有被标准GRPO纳入Advantage。

核心方法(Outcome + Process Advantage Shaping) ​

📕核心方法

Outcome-Verifiable Reward
  • 每个AppWorld任务包含 M 个状态Unit Test。
  • Trajectory Reward为通过测试的比例：
Ri=1M∑j=1Mpass(uj,τi)
  • Group-relative Outcome Advantage使用去均值但不除以标准差：
A^i,t=Ri−mean({Ri}i=1G)
Process-Verifiable Advantage Shaping
  • 将生成Token分为执行成功Step的 Iisucc、执行失败Step的 Iifail；Observation Token不参与更新。
  • 成功Step保持原Outcome Advantage。
  • 失败Step根据Trajectory Outcome做不同修正：
    • A^=0：施加固定惩罚 −b。
    • A^<0：放大负优势为 (1+b)A^。
    • 其他情况：置0，避免成功Trajectory中的失败Token得到正强化。
  • 论文使用 b=0.2。

GVPO目标

JGVPO=1G∑i1|τi|∑tmin(ai,tAi,t,clip(ai,t,1−ϵlow,1+ϵhigh)Ai,t)
  • 使用非对称Clip (0.2,0.28)，给正向概率更新更大空间以维持探索。

实验设置 ​

✍️实验设置

实验设置

基础模型

  • Qwen2.5-32B-Instruct。

训练任务/数据

  • AppWorld Difficulty 1/2：72个任务，24个Scenario。
  • 每个任务8条Rollout；最大40轮交互。

评测任务/数据

  • AppWorld Test-Normal：168个任务、56个Scenario。
  • AppWorld Test-Challenge：417个任务、139个Scenario，最大50轮交互。
  • 指标：TGC与SGC。

算法/策略

  • 与GRPO、GRPO+KL、GSPO、DAPO、Dr.GRPO、RLOO和LOOP比较。
  • 使用Unit Test Outcome Reward；GVPO额外使用中间代码执行反馈。

超参

  • Group Size 8，Learning Rate 1×10−5，训练144步。
  • Training/Eval Temperature：1.0 / 0.0。
  • 8张H100，veRL + FSDP2 + vLLM。

设计消融

  • Loss聚合很重要：改为Token-Mean，Test-C直接降到34.6 / 15.1。

未来方向 ​

⛳未来方向

未来方向
  • GVPO依赖确定性环境和可明确识别的Process Signal；噪声反馈、模糊成功标准下尚未验证。
  • 失败Step当前只按执行成功/失败二分，未来可加入Partial Test、状态变化和更细错误类型。
  • Advantage Shaping后不再满足零均值无偏性质，需要进一步分析长期训练稳定性与偏差。
  • Process Penalty会改变Agent行为偏好，应研究如何避免过度查询文档或过度保守。

(2604) Skill-SD: Skill-Conditioned Self-Distillation for Multi-turn LLM Agents ​

🌺 论文摘要

Skill-SD 论文摘要

参考链接

  • paper

核心方法

  • Skill-SD：GRPO结果奖励 + Skill条件下的Token级自蒸馏。
  • 从Agent自己的Trajectory中总结三类Skill：成功经验、错误教训、高层Workflow。
  • Skill只给Teacher看：
    • Student始终使用Plain Prompt做On-policy Rollout。
    • Teacher额外看到Skill，并给同一条Token序列重新打分。
  • Teacher参数从最新Student同步，使用Importance-Weighted Reverse-KL把Skill信息蒸馏回Student。
  • 测试时Student不需要Skill，避免Train/Test Prompt不一致。

模型效果 (Qwen3-4B-Instruct-2507)

  • AppWorld 57-task Dev：Accuracy 64.9，Completion 84.9。
  • Vanilla GRPO：Accuracy 50.9，Completion 76.3；Skill-SD提升+14.0 Accuracy。
  • Skill直接注入Student的Skill-Augmented GRPO只有42.1 Accuracy，低于Vanilla GRPO。

重要结论

  • Skill应该指导Teacher，而不是直接喂给Student：否则容易过拟合Skill Prompt，并造成Train/Test条件不一致。
  • Rollout必须由Student产生：Teacher自己采样会变成Off-policy，训练中期容易Collapse。
  • Teacher不能冻结：Frozen Teacher虽然不崩，但会逐渐落后于Student，最终平台更低。
  • 蒸馏不能替代RL：
    • RL回答哪条Trajectory值得学。
    • Self-Distillation回答轨迹里哪些Token如何学得更细。

关键贡献

  • 用Trajectory-derived Skill替代Agent任务中不存在的唯一Ground-truth Answer，构造动态Teacher Signal。
  • 推导跨Prompt自蒸馏的Importance-Weighted Reverse-KL，修正直接微分 k3 的梯度偏差。
  • 证明动态Teacher-Student共演化和On-policy采样对长程Agent自蒸馏不可缺少。

问题背景(稀疏奖励与固定Teacher Signal) ​

❓问题背景

Agent任务难以直接套用Self-Distillation

RL样本效率问题

  • AppWorld等长程任务只有延迟Outcome Reward，很难判断哪些Action Token真正有用。
  • On-policy Self-Distillation可以用Teacher提供Dense Token Supervision，但通常假设存在固定正确答案。

Agent任务的多解性

  • 同一个AppWorld任务可以通过不同API顺序完成，不存在唯一标准Trajectory。
  • 固定参考答案会限制Student探索，并把一种实现路径误当成唯一正确策略。

训练稳定性问题

  • Teacher与Student看到不同Prompt，Token分布存在Cross-Prompt Mismatch。
  • 若Teacher自己生成Rollout，随着Student更新，Off-policy Importance Ratio会逐渐失稳。

核心方法(Skill-Conditioned Self-Distillation) ​

📕核心方法

Trajectory-derived Skill与UCB检索
  • Agent完成任务后，辅助LLM将Trajectory总结为：
    • esuccess：哪些行为有效。
    • emistake：哪些错误需要避免。
    • eworkflow：下次可复用的高层流程。
  • 不存储完整Trajectory，避免单一路径约束多解任务。
  • 每个任务维护自己的Skill Buffer，通过UCB在利用高回报Skill和探索新Skill之间平衡：
score(e)=r¯(e)+cln⁡Nucbn(e)
Teacher/Student分离
  • Student Policy：πθstu(⋅|x,y<t)，仅看Plain Prompt，并负责On-policy Rollout。
  • Teacher Policy：πθ¯tea(⋅|x⊕S(x),y<t)，额外看到检索Skill。
  • Teacher在每次Iteration从最新Student同步，Skill只改变条件Context，不进入测试时Student接口。

作用分工

  • GRPO：根据Trajectory Reward决定哪条轨迹值得强化。
  • Self-Distillation：决定轨迹内部的Token概率如何移动。
Importance-Weighted Reverse-KL
  • 对Student On-policy生成的同一Token序列，分别用Plain Student和Skill Teacher重新计算Log Probability。
  • 定义Student/Teacher Log Ratio：
ℓi,t=log⁡πθstu(yi,t|x,yi,<t)−log⁡πθ¯tea(yi,t|x⊕S(x),yi,<t)
  • 使用On-policy Importance Weight ρon 修正采样分布，并优化：
LSDL=1N∑i,tρi,ton(e−ℓi,t−1+ℓi,t)
  • 总目标：Ltotal=LGRPO+λLSDL，论文最优 λ=0.001。

1. Sequential Rollout

  • 利用 AppWorld 的 Scenario 结构（每个场景包含3个相似任务）。
  • 构建任务链 (q1,q2)：

    • 技能生成奖励：如果 q1 生成的技能帮助成功解决q2，则奖励 q1。

  • 算法：GRPO (Group Relative Policy Optimization)。

(2510) SALT: Step-level Advantage Assignment for Long-horizon Agents via Trajectory Graph ​

🌺 论文摘要

SALT 论文摘要

参考链接

  • SALT: Step-level Advantage Assignment for Long-horizon Agents via Trajectory Graph

核心方法

  • SALT 框架：基于轨迹图构建的细粒度优势分配机制。
  • 核心思想：将多个生成的轨迹合并为轨迹图 (Trajectory Graph)。
    • 合并 (Merge)：不同轨迹中相同状态和动作的节点合并。
    • 分支 (Diverge)：不同动作导致路径分叉。
  • 优势重估：基于图结构计算每个Step的优势，而非简单广播整个轨迹的最终回报。
    • 共享步骤（出现在成功和失败中）-> 中性优势。
    • 关键步骤（仅出现在成功轨迹中）-> 高优势。
  • 轻量级插件：无缝集成至 GRPO/RLOO，无需额外Reward Model，无需人工标注。

模型效果 (Qwen2.5-1.5B/7B/32B)

  • ALFWorld: Qwen2.5-1.5B 上，GRPO 成功率从 69.0% 提升至 80.5% (+11.5%)。
  • WebShop: Qwen2.5-1.5B 上，GRPO 成功率从 64.6% 提升至 66.2%。
  • AppWorld: Qwen2.5-32B 上，GRPO+SALT 在 Test-Normal SGC 指标上达 20.9% (Base GRPO 17.0%)。

重要结论

  • 细粒度信贷分配：解决了长程任务中好坏动作纠缠导致梯度冲突的问题。
  • 计算开销极低：相比Rollout和Update，SALT引入的开销可忽略不计。
  • 无需Critic模型：适用于 Group-Based RL (如 GRPO) 的纯 Policy 优化场景。

关键贡献

  • 提出了基于结果稀疏奖励进行Step-level 优势估计的通用方法 SALT。

问题背景 ​

❓问题背景

现有 Group-based RL 的局限性

长程任务挑战

  • LLM Agent 在 WebShop、ALFWorld 等长程任务中，需要执行多步操作才能获得最终反馈。
  • 主流方法（如 GRPO）通常依赖稀疏的最终奖励 (Outcome-based rewards)。

粗粒度信用分配 (Coarse-grained Credit Assignment)

  • GRPO 将整条轨迹的最终回报直接广播给轨迹中的每一个 Step。
  • 噪声问题：
    • 成功轨迹中可能包含冗余/错误步骤（被错误奖励）。
    • 失败轨迹中可能包含正确步骤（被错误惩罚）。
  • 后果：导致训练不稳定，策略更新存在梯度冲突，难以收敛到最优解。

核心方法(Step-level Advantage Assignment) ​

📕核心方法

SALT: Step-level Advantage Assignment

1. 轨迹图构建 (Trajectory Graph Construction)

  • 输入：对同一个 Prompt 采样的 G 条轨迹 (Rollouts)。
  • 操作：
    • 定义状态 st 为包含过去 h 步的历史窗口。
    • Merge：如果两条轨迹在某一步的 历史状态 和 当前动作 相同，则将它们视为图中的同一个节点。
    • Diverge：动作不同则产生分支。
  • 结果：将独立的线性轨迹转化为有向无环图 (DAG)，揭示了哪些步骤是跨轨迹共享的，哪些是独有的。

2. 细粒度优势计算 (Step-level Advantage)

  • 直觉：
    • 共享节点 (Shared Nodes)：出现在多条轨迹（包括成功和失败）中，说明该步骤对结果区分度低，应给予平均/中性优势。
    • 独有节点 (Distinct Nodes)：仅出现在高分轨迹中的步骤可能是关键成功因素，应给予高优势。
  • 计算：
    • 每个节点的价值 V(s,a) 估计为经过该节点的所有轨迹回报的平均值。
    • 使用该节点价值替代原有的轨迹级回报来计算优势函数。

3. 轻量化与兼容性

  • Plug-and-Play：插入在 Advantage Computation 和 Policy Update 之间。
  • 零额外参数：不需要训练 Value Model 或 Process Reward Model (PRM)。

  • 计算开销：在一次迭代中，Rollout 耗时 240s，SALT 仅耗时 0.15s。相比带来的性能提升，开销几乎可以忽略不计。

  • Group Size：Group Size 越大 (如 16)，轨迹图连接越丰富，SALT 带来的相对提升越大。

ProST-渐进式子任务训练 ​

ProST 训练策略

核心思想

  • 借鉴课程学习，让模型先学简单的/局部的，再学复杂的/全局的。
  • 训练早期，只暴露部分子任务。
  • 随Epoch增加，逐步扩展输入上下文，直到覆盖完整轨迹。

训练流程

  • 数据构建：包含 N 个子任务的轨迹。
  • 渐进式掩码 (Progressive Masking)：
    • Epoch 0：仅训练特定的子任务子集（例如子任务 2, 3），屏蔽其他。
    • Epoch i：引入更多子任务（例如从子任务 2 扩展到 1-3）。
    • Final Epoch：训练包含所有子任务的完整轨迹。
  • 优势：
    • 避免模型在长序列中迷失。
    • 强制模型优先掌握核心逻辑，再处理长依赖。

Mask错误动作的Loss

  • 仅计算正确步骤和自我修正成功步骤的Loss。
  • Mask错误步骤的Loss，避免模型学习错误的推理路径。
  • 同 SWE-Lego Mask错误动作

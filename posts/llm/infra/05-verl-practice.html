训推节点和副本数 ​

训推节点和副本

节点

  • trainer.nnodes：训练节点
  • rollout.nnodes：推理节点

llm 推理副本数

  • 推理 GPU：4 节点 × 8 卡 = 32 卡

  • 每个副本：rollout_tp = 2, (pp=dp=1)，占 2 卡

  • 推理副本数：32 ÷ 2 = 16 个 SGLang 副本

BatchSize 和 required_samples 样本数 ​

Batch和required_samples 样本数

Batch 和 required_samples 样本

  • ppo_mini_batch_size：ppo一次更新参数所需的bs，后续会乘以rollout.n
  • require_batches：一次训练需要的batch数
  • required_samples：一次训练需要的sample数，require_batches * ppo_mini_bs
    • 这里的samples，是group的概念，后续才乘以rollout_n
    • fully_async 参数源代码笔记

样本陈旧度

  • staleness_threshold：样本陈旧度，采样端领先训练端，1 + staleness

最大需要样本数

  • max_required_samples：required_samples * (1 + staleness) * trigger_sync_step
  • max_queue_size：结果队列容量 大小同 max_required_samples，已完成等待trainer消费

权重同步

  • trigger_parameter_sync_step：trainer执行几轮后，向推理端同步 1 次更新权重。

rollout 并发度 ​

rollout 并发

llm 并发

  • concurrent_samples_per_replica：每个llm副本的最大group并发，默认为16
    • sample 为 group-level，实际轨迹需要 乘以 rollout_n

轨迹并发

  • max_concurrent_samples：min(llm 副本数 * 单副本并发数, max_required_samples)
  • total_train_steps：total_rollout_steps / (required_samples * trigger_sync_step)

rollout 侧 ​

rollout 侧

llm 副本

  • rollout，4节点，32卡，每个副本TP=2，一共 32/2=16个副本

轨迹数量

  • required_samples = 1 * 128 = 128组 = 128 * 16 = 2048 轨迹
  • max_required_samples = required_samples * (1 + staleness) * sync_step =
    • 128 * (1+2) * 1 = 384组 = 6144 轨迹
  • 2048轨迹，16个副本，每个副本处理 2048/16=128 轨迹

rollout 并发

  • max_concurrent_samples：min(llm 副本数 * 单副本并发数, max_required_samples)
    • min (16*16, 384) = 256 组 = 4096 轨迹
  • 最多256组同时执行，此处可能受到环境的限制，即初始化环境需要等待。
参数含义
required_samples=128Trainer 每次取 128 组数据进行训练
max_concurrent_samples=256Rollout 同时最多执行 256 组任务
max_required_samples=384限制 Rollout 提前生产的数据额度，防止旧策略数据过多

训练侧 ​

训练侧

核心配置推算

  • train，8节点，64卡，tp=2, pp=2, cp=4，计算出 DP=4

    DP=n_gpusTP×PP×CP=642×2×4=4

  • 2048条轨迹，有4路数据并行，每路分到 2048 / 4 = 512条轨迹

  • micro_batch_size=1 梯度累计，每路需要处理 512个 micro_batch

    M=2048DP×micro_bs=20484×1=512个 micro_batch

  • 这512个 micro_batch 梯度累计完成后，完成1次 optimizer 更新。

总结

  • 64 训练卡，实际 4 路数据并行，每路累积 512 个 micro-batch 梯度
  • 归约4路梯度后，基于全部2048轨迹，完成一次全局参数更新。

单步及Epoch时间 ​

提示

步数

  • 假设 6000数据，bs=128，step=6000/128=46步。
  • 假设 rollout 一批 需要40分钟，训练需要 32分钟。

同步共卡方案

  • 2阶段串行：比如 40+32=72分钟

    Tstep≈Trollout+T训练+T模型切换及同步

  • 46*72=3312分钟=55小时=2天7小时

异步分离方案

  • 两阶段充分重叠：比如 max(40,32)=40分钟，也就是训练32分钟，等数据8分钟，就是40分钟

    Tinterval≈max(T生产一批数据,T消费一批数据)+T无法重叠的开销

  • 46*40=1840分钟=30小时=1天6小时

@ray.remote(num_cpus=1)
class SGLangHttpServer:
    def __init__(
        self,
        config: RolloutConfig,
        model_config: HFModelConfig,
        rollout_mode: RolloutMode,
        workers: list[ActorHandle],
        replica_rank: int,
        node_rank: int,
        nnodes: int,
        cuda_visible_devices: str,
    ):
        print(f"SGLang http server: {rollout_mode=}, {replica_rank=}, {node_rank=}, {nnodes=}, {cuda_visible_devices=}")
        os.environ["CUDA_VISIBLE_DEVICES"] = cuda_visible_devices
        assert torch.cuda.is_available(), "SGLang http server should run on GPU node"

        self.config: RolloutConfig = omega_conf_to_dataclass(config)
        self.model_config: HFModelConfig = omega_conf_to_dataclass(model_config, dataclass_type=HFModelConfig)
        self.config.max_model_len = self.config.prompt_length + self.config.response_length 
        self.rollout_mode = rollout_mode
        self.workers = workers

        self.replica_rank = replica_rank
        self.node_rank = node_rank
        self.nnodes = nnodes

    async def generate(
        self,
        prompt_ids: torch.Tensor,
        sampling_params: dict[str, Any],
        request_id: str,
        image_data: Optional[list[Any]] = None,
    ) -> TokenOutput:
        """Generate sequence with token-in-token-out."""
        max_new_tokens = min(self.config.response_length, self.config.max_model_len - len(prompt_ids) - 1) 
        sampling_params["max_new_tokens"] = max_new_tokens
        return_logprob = sampling_params.pop("logprobs", False)

        request = GenerateReqInput(
            rid=request_id,
            input_ids=prompt_ids,
            sampling_params=sampling_params,
            return_logprob=return_logprob,
            image_data=image_data,
        )
        output = await self.tokenizer_manager.generate_request(request, None).__anext__()
        if return_logprob:
            output_token_logprobs = output["meta_info"]["output_token_logprobs"]
            log_probs, token_ids = zip(
                *[(log_prob, token_ids) for log_prob, token_ids, _ in output_token_logprobs], strict=True
            )
        else:
            token_ids = output["output_ids"]
            log_probs = None
        return TokenOutput(token_ids=token_ids, log_probs=log_probs)

batch_size相关 ​

简单总结 ​

batch_size 总结
  • data.train_batch_size
    • 训练batch大小，乘以rollout.n，得到real_train_batch_size
  • actor.ppo_mini_batch_size
    • 更新模型时，对real_train_batch划分为多个mini_batch
    • 1个real_train_batch 更新多次；1个mini_batch 更新1次
  • actor.ppo_micro_batch_size_per_gpu
    • 更新模型时，对mini_batch划分为多个micro_batch，依次计算，梯度累积
    • micro_batch_size=ppo_micro_batch_size_per_gpu
  • rollout.log_prob_micro_batch_size_per_gpu
    • 计算old_log_prob时，对real_train_batch划分为多个micro_batch，依次计算
  • ref.log_prob_micro_batch_size_per_gpu
    • 计算ref_log_prob时，对real_train_batch划分为多个micro_batch，依次计算

data.train_batch_size ​

data.train_batch_size

含义

  • train_batch_size：训练集batch大小，用于数据迭代加载训练
  • val_batch_size：同理， 不再赘述

关键点

  • 与rollout.n结合，构建出real_train_batch_size
    • real_train_batch_size = train_batch_size * rollout.n

actor.ppo_micro_batch_size_per_gpu (梯度累积) ​

actor.ppo_micro_batch_size_per_gpu (梯度累积)

背景

  • 一次前向反向更新会OOM，因此拆分成多步。
  • 梯度累积：计算出梯度，但不清零，多步累积，最后一次性更新。

含义

  • update actor(或critic)时，对当前mini_batch进行划分
    • 划分为多个micro-batches
      • micro_batch_size = ppo_micro_batch_size_per_gpu
    • 本质就是梯度累积步数
  • real_train_batch_size -> ppo_mini_batch_size -> ppo_micro_batch_size_per_gpu

Critic同理

  • 参数为critic.ppo_mini_batch_size_per_gpu

以下3者有相似处

  • rollout.log_prob_micro_batch_size_per_gpu
    • 计算old_log_prob，划分real_train_batch
  • ref.log_prob_micro_batch_size_per_gpu
    • 计算ref_log_prob，划分real_train_batch
  • actor.ppo_micro_batch_size_per_gpu
    • 更新模型+梯度相关，划分mini-batch
ppo_micro_batch_size_per_gpu 注意事项
  • 这个值可能和RL学习稳定性有关系，小的数值+大的学习率，可能会导致训练崩塌。
  • 原因：单次梯度计算依赖的样本数量。
    • 如果太小，可能导致梯度估算的方差大，噪声大， 信噪比更低
    • 策略网络容易更新错误，被带偏了。
  • 需观测相关指标：pg_loss, kl_loss, entropy，advantages等等。

并行参数计算 ​

并行参数计算

实际训练bs

  • real_train_batch_size = data.train_batch_size * rollout.n

总GPU数量

  • n_gpus = n_gpus_per_node * nnodes

模型并行

  • mp = tp * pp
  • model_parallel_size = tensor_model_parallel_size * pipeline_model_parallel_size

数据并行

  • dp = n_gpus // (mp * cp)
  • megatron_dp = n_gpus // (model_parallel_size * context_parallel_size )

实际训练最小bs

  • mini_bs = dp * micro_bs_per_gpu
  • minimal_bsz = megatron_dp * actor.ppo_micro_batch_size_per_gpu

rollout llm 副本数

  • rollout_replicas：n_gpus // rollout. tp*pp*dp
  • 每个副本最大并发：concurrent_samples_per_replica数

并行参数约束条件

实际train_bs被mini_bs整除

  • real_train_batch_size % minimal_bsz == 0

TP：注意力头数/GQA组数 整除

  • num_attention_heads % tp == 0
  • num_query_groups % tp == 0，非常重要!!

PP：总层数整除

  • num_layers % pp == 0

EP：专家数量整除

  • num_moe_experts % ep == 0

EP分组：专家数量整除

  • num_moe_experts % moe_router_num_groups == 0

Expert DP：专家数据并行度，DP 整除EP

  • Expert DP = DP / EP

TP/PP/CP参数：GPU数量整除

  • n_gpus % mp * cp == 0 ，非常重要!!
  • n_gpus % tp * pp * cp == 0
一些原理
  • TP：切分Attention/MLP
    • TP越大：单卡KV Cache压力小，支持Context越长
    • 缺点：受限于KV Heads数量；跨节点通信慢。
  • EP：切分Experts
    • EP越大：单价存单专家越少，静态显存占用低
    • 缺点：引入All-to-All通信，动态显存变大。长文本下，EP太大，Buffer可能撑爆显存。
  • 通信效率
    • 节点内：适合TP和EP通信
    • 节点间：适合DP通信，梯度同步，通信量小
    • 尽量让TP和EP都在一台机器内，解决。

模型合并
  • 切记不要像官网一样使用--tie-word-embedding这个参数，这会导致不存储lm_head.weight，这样会导致转换成hfmodel部署时，预测会出错，乱码、不停止。
  • 保存后的tokenizer_config.json，没有chat_template这个参数，原基模是有的，可以复制粘贴过来。

合并脚本如下：

bash
local_dir="xxx"
target_dir="xxx"

python -m verl.model_merger merge \
    --backend megatron \
    --local_dir ${local_dir} \
    --target_dir ${target_dir} \
